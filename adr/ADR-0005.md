# ADR-0005: New `emailQueue` Table + Data-Backed Notification Services

**Status**: Accepted
**Date**: 2026-08-18
**Decision**: SPEC-0008 introduces a NEW `emailQueue` table (additive, reversible) as the
durable backing store for the email notification queue, and the completed Sms/Email
services live in the Data project following the `IHolidayService` placement precedent
(research D-1/D-7). The legacy app had no email queue — legacy email was synchronous
CDO/OSSMTP per spec §6.7.

## Context

SPEC-0008 (notifications, content, reporting) requires a durable email notification
queue (FR-002/FR-003) with a send-once gate and retry semantics (AC-004/AC-005). The
legacy `VisaEntry` app has an SMS queue (`smsQueue` → `smshistory`) but **no email
queue** — email was sent synchronously via CDO/OSSMTP (spec §6.7). Research decision
D-1 (research.md L21) therefore mandates a NEW `emailQueue` table; D-7 (research.md
L84) mandates that the completed Sms/Email services follow the `IHolidayService`
placement precedent (implementations in the Data project, not Core placeholders).

## Decision

1. **New `emailQueue` table** (additive, reversible): `id` (identity), `toemail`,
   `subject`, `body`, `agentsid`, `refno`, `awb`, `sentby`, `sentdate`. Registered in
   spec §16 + Assumptions (traceability from checklist CHK002/CHK014/CHK038; task
   T001). No legacy table is altered or dropped (spec §16; reversibility tests cover
   this).
2. **Drain to `sentmails`**: enqueued emails are drained transactionally to the
   existing append-only `sentmails` table (research D-3) — the audit row and the
   queue-row deletion commit together (send-once gate, mirroring the legacy SMS
   behavior). Failed rows are retained in the queue for the worker's next pass (§18 —
   no message loss, no silent drop).
3. **Data-backed services**: `SmsService`/`EmailService` are implemented in
   `src/VisaFusion.Data/Application` (EF-backed, `IHolidayService` precedent, D-7);
   the placeholder `ISmsService`/`IEmailService` registrations were removed from
   `src/VisaFusion.Core/CoreServiceCollectionExtensions.cs` (task T014).

## Alternatives Considered

1. **Reuse `smsQueue` for email** — rejected: the legacy `smsQueue` schema has no
   `subject`/`body` columns and is SMS-specific; mixing channels would break the
   append-only audit contract (FR-006/BR-003).
2. **Synchronous email (legacy behavior)** — rejected: FR-002/FR-003 require a durable
   queue with retry and a send-once gate; synchronous CDO/OSSMTP cannot survive
   provider failures without message loss.
3. **Keep Core placeholders** — rejected: D-7 (research.md L84) — completed services
   follow the `IHolidayService` placement precedent in the Data project; Core holds
   only the abstractions.

## Consequences

- `emailQueue` is a NEW additive table; the six legacy tables (`smshistory`,
  `smsQueue`, `sentmails`, `dailyUpdate`, `holidaylist`, `weeklyoff`) are unchanged
  (spec §16).
- The email drain writes to `sentmails` with `agentsid` NOT NULL (0 = no agent, e.g.
  the office contact-query notification email, AC-002).
- Reversibility: the additive migration can be rolled back without touching legacy
  tables (SPEC-0004 reversibility tests).
- Full test suite stays green: Unit 239/239, Functional 240/240, Integration 77/77
  (incl. the new BR-001 audit-continuity test, T050).
