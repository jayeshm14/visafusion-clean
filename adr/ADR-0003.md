# ADR-0003: Migration Tooling as a Dedicated Console Project (VisaFusion.Migration)

**Status**: Accepted
**Date**: 2026-08-10
**Decision**: The complete data-model migration (SPEC-0004) is implemented as a new
dedicated console project `src/VisaFusion.Migration` inside the existing `VisaFusion.sln`,
referencing `VisaFusion.Data` (target DbContext/entities/EF migrations) and
`VisaFusion.Identity` (password hashing). The target schema is defined by EF Core
migrations in `VisaFusion.Data`; the migration tool is an operator-run, offline process
with a fixed command sequence (`preflight → snapshot → schema → copy → cleanse →
identity → validate → report`) and documented exit codes 0–5.

## Context

SPEC-0004 requires migrating all 52 legacy `VisaEntry` tables into the target
`VisaFusion` schema with zero data loss, reconstructed primary keys, foreign keys and
indexes, three legacy identity sources imported into ASP.NET Core Identity (passwords
hashed on import), approved cleansing rules gated by business sign-off, and a
machine-readable migration report (FR-001…FR-009, BR-001…BR-005, NFR-002…NFR-006).

The migration is a **one-shot, offline, operator-run process** (legacy app stopped for
the maintenance window, NFR-002) — not a runtime surface. The SPEC-0003 target
architecture fixed the six physical projects (`Core`, `Data`, `Identity`, `Api`, `Web`,
`Jobs`); none of them is a natural home for a batch migration pipeline:

1. **`VisaFusion.Data`** owns the target schema (DbContext, entities, EF migrations)
   but is a class library — it must not host an executable entry point or operator CLI.
2. **`VisaFusion.Web`/`VisaFusion.Api`** are runtime hosts; a migration CLI must not be
   reachable as an HTTP surface (no anonymous write endpoints, security by default).
3. **`VisaFusion.Jobs`** runs background workers against the live app; the migration is
   explicitly offline and must not share the runtime's lifecycle or configuration.

The legacy app is the source of truth and is **never modified** (FR-008, AC-006); the
migration reads it read-only and writes only to the target `VisaFusion` database.

## Decision

1. **New console project** `src/VisaFusion.Migration` (net8.0, C# 12) added to
   `VisaFusion.sln`, referencing `VisaFusion.Data` and `VisaFusion.Identity`.
2. **Fixed command order** enforced by the CLI runner and the `StepRunner`
   predecessor guard (contracts/migration-cli.md §2): `preflight → snapshot → schema →
   copy → cleanse → identity → validate → report`. A step may not run before its
   predecessor completes successfully; out-of-order or unknown steps fail fast with
   exit 1 and a precise message (ADR-0004).
3. **Exit codes** 0–5 per contracts/migration-cli.md §4: 0 success, 1 preflight
   failure, 2 step failure (incl. data-quality gaps), 3 validation discrepancies,
   4 integrity violation, 5 configuration error.
4. **Target schema via EF Core migrations** in `VisaFusion.Data/Migrations/`
   (initial migration created with `dotnet ef migrations add InitialCreate`); the
   `schema` step runs `Database.Migrate()` on the target. `__EFMigrationsHistory` is
   the standard tooling artifact (spec §16).
5. **Read-only legacy access** via `Microsoft.Data.SqlClient` with parameterized
   queries only (NFR-003); bulk copy via `SqlBulkCopy` in FK-dependency order with
   bounded batch sizes (FR-002, spec §13); identity values round-tripped with
   `IDENTITY_INSERT` where the legacy table has an identity column (FR-003).
6. **Deterministic gap handling**: undocumented data-quality issues (e.g. GAP-0002,
   `agents.agentsID = 4114` duplicate) stop the copy with exit 2 and a gap report —
   the tool never guesses (library/01).
7. **Structured logging** via Serilog (console + file + SQL sinks, NFR-006);
   connection strings from environment/user-secrets only, placeholders in
   `appsettings.json` (NFR-004).
8. **No runtime surface**: the project is a console executable, not referenced by
   Web/Api/Jobs; no HTTP endpoints, no anonymous write paths.

## Alternatives Considered

1. **Host the migration in `VisaFusion.Jobs` as a one-shot worker** — rejected: Jobs
   runs against the live runtime lifecycle; the migration is offline-only and must not
   be triggerable from the running app. Mixing them couples the maintenance window to
   the runtime and risks accidental execution.
2. **A scripted T-SQL migration (no .NET tool)** — rejected: violates the
   deterministic, testable, traceable requirements (constitution Principle V); no
   automated tests, no structured reporting, no sign-off gating, and string-concatenated
   SQL risk (NFR-003).
3. **Extend `VisaFusion.Data` with a CLI entry point** — rejected: a class library
   should not own an executable; the migration's operator concerns (commands, run-state,
   reporting) would pollute the persistence project.
4. **A separate repository/solution for the tool** — rejected: the migration is a
   feature of this modernization (SPEC-0004) and must share the target schema model and
   Identity hashing; a separate repo would break traceability and single-source-of-truth
   (GitHub, constitution Principle IV).

## Consequences

- The migration pipeline is independently buildable, testable, and runnable by an
  operator; all 8 steps are registered in fixed order and covered by unit/integration/
  functional tests (51+ tests, all green as of 2026-08-10).
- The target schema stays defined in one place (`VisaFusion.Data` EF model), so the
  runtime app and the migration tool can never drift.
- The tool is safe by construction: read-only on legacy, no HTTP surface, no secrets
  in source, no plaintext passwords (BR-002), no string-concatenated SQL (NFR-003).
- The migration cannot complete end-to-end until the GAP-0002 owner decision and the
  pre-migration backup exist (AC-008) — by design, the tool reports these as gaps
  rather than guessing.
