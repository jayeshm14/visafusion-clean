# ADR-0001: Target Architecture and Specs Layout

**Status**: Accepted
**Date**: 2026-08-06
**Decision**: Target platform architecture + specs layout reconciliation for VisaFusion.

## Context

The legacy VisaEntry application is Classic ASP / VBScript with ADODB against SQL Server
(52 tables, 585 live root ASP files, production data 2001-12-02 → 2026-04-21). The
constitution (`library/01`, `.specify/memory/constitution.md`) mandates a deterministic
modernization to ASP.NET Core with Specification-Driven Development, an AI-native
Knowledge Graph, and SpecKit governance.

Two structural tensions required an explicit decision:

1. The constitution (`library/03 §3`) mandates specifications under category subfolders
   (`/specs/epics`, `/specs/features`, `/specs/modules`, `/specs/database`, `/specs/api`,
   `/specs/ui`, `/specs/security`, `/specs/migration`, `/specs/testing`) with `SPEC-XXXX`
   identifiers, while SpecKit's native `/speckit.specify` flow (configured with
   `feature_numbering: sequential`) creates a flat `specs/NNN-<short-name>/spec.md` layout
   and resolves the active feature via `.specify/feature.json`.
2. The target .NET stack must be fixed and documented to keep every subsequent decision
   deterministic.

## Decision

### Architecture

- **Platform**: ASP.NET Core (Razor Pages for back-office UI, Web API for integrations).
- **Persistence**: EF Core against the existing SQL Server `VisaEntry` database.
- **Identity**: ASP.NET Core Identity with role-based and policy-based authorization.
- **Solution**: `VisaFusion`, structured per `library/08 §2`
  (`src/` + `tests/` with Domain, Application, Infrastructure, Persistence, Identity, Api,
  Web, Shared).
- **Design approach**: Clean Architecture + DDD with the bounded contexts named in
  `library/07 §3`; C4 diagrams version-controlled; every architectural change requires an
  ADR.
- **Knowledge Graph**: maintained as a versioned artifact (JSON + traceability matrix)
  per `library/04`, updated after every completed task.
- **ADRs**: stored in `/adr` as `ADR-XXXX.md`.

### Specs Layout Reconciliation

- **Feature specifications** (produced by `/speckit.specify`) use the SpecKit-native
  layout `specs/NNN-<short-name>/spec.md`, because the SpecKit tooling resolves the active
  feature from `.specify/feature.json` and the sequential numbering scheme. This is the
  execution path for per-module specs.
- **Category folders** (`epics`, `features`, `modules`, `database`, `api`, `ui`,
  `security`, `migration`, `testing`) remain for organizational and cross-cutting
  specifications, and each feature spec carries a `Category` field mapping to one of them.
- **Identifier**: each feature spec embeds `SPEC-XXXX` in its Identifier section (section 1
  of the 24-section template), preserving the traceability requirement regardless of
  folder.
- `library/03 §3` is updated to document this reconciliation.

## Alternatives Considered

1. **Category-subfolder-only layout (constitution as originally written)** — rejected:
   incompatible with SpecKit tooling resolution (`feature.json`), would require manual
   path overrides on every `/speckit.specify` invocation.
2. **SpecKit-native-only layout, delete category folders** — rejected: category folders
   provide useful organization for epics and cross-cutting specs and are referenced by the
   constitution command.
3. **Legacy migration by manual translation** — rejected: violates SDD and traceability
   requirements; the constitution mandates specifications before implementation.

## Consequences

- Feature specs are produced by the standard SpecKit flow with zero tooling friction.
- Traceability is preserved via embedded `SPEC-XXXX` identifiers and the 24-section
  template override.
- The category folders remain but are no longer the sole location for feature specs —
  documented in `library/03 §3` to prevent ambiguity.
- ADR-0001 becomes the architectural reference for all subsequent ADRs.
